# Nexus V3.1 規格：瀏覽器「交給節點下載」（讓 Pornhub 這類網站也能用節點下載）— 草稿

> 2026-11-23｜狀態：**完成**（電腦版 v1.32.0～v1.32.2、腳本 v3.22.0）。**U-01 2026-11-24 使用者在台灣實機通過**（Pornhub 經「🖧 交給節點」節點下載成功）；E4 自動測試在 GitHub（美國）測試不成立（影片伺服器擋那台機器）。
> 起因：V3 實機驗收發現 Pornhub 對「不是瀏覽器的程式」開網頁回 **HTTP 410**（`08-V3交付報告.md` 3.5）；XVideos 節點下載正常。

## 1. 做法（白話）

瀏覽器本來就拿得到影片真正的位址（電腦版的「送到電腦版」就是這樣繞過 410 的）。
V3.1 在瀏覽器腳本的下載面板加一個「**🖧 交給節點**」：腳本把「網頁網址＋影片真正的位址＋標題＋畫質」送給電腦版（Master），
Master 建一個 `video.download` 任務、附上影片位址；節點**不用再開網頁**，直接在沙箱裡下載那個影片檔。

```
瀏覽器腳本 ──(本機 Bridge，已配對)──▶ 電腦版 Master ──(mTLS 派任務)──▶ 節點沙箱 ──▶ 影片伺服器（phncdn.com…）
```

**不採用**的做法：讓節點「假裝成瀏覽器」（yt-dlp 偽裝需要 `curl_cffi`，它用 C 自己連網，會繞過沙箱的網路檢查 → 等於拆掉一層保護）。

## 3. 安全規則（不因為這個功能放寬）

- 影片位址一樣過三層檢查：Master 建任務時 `static_check(kind="any")`；而且**影片位址和網頁要是同一個網站**（`sites.site_name` 一致，例如 Pornhub 網頁只能配 phncdn.com）；子程序 socket 層照舊（清單網域、443、公開 IP）
- 只接受 https、長度 ≤ 4096；不准帳號密碼、不准 IP
- 協定：直接檔（mp4）或 HLS（m3u8，native 下載）；其他拒絕
- Bridge 端照舊要 6 位數配對；瀏覽器送來的東西只是「建議」，Master 一樣全部重新驗證
- 標題只拿來當檔名，照舊 `sanitize_filename`

## 5. 已知風險（照實說）

- **影片位址有時效**（Pornhub 的位址幾十分鐘到幾小時會過期）、**可能綁 IP**：同一個家裡的網路（瀏覽器和節點出口 IP 一樣）應該沒問題；跨網路可能失敗 → 會回「影片位址過期或被拒，請重新從瀏覽器送」
- 任務的 `expires_at` 縮短成 30 分鐘（位址過期後排隊再久也沒用）
- **E4 的自動測試可能測不到**：GitHub 的機器在美國，Pornhub 在美國部分州會擋（回 410／年齡驗證）；測不到時報告會寫「地區限制、測試不成立」，不會說成通過

## 6. 驗收

- U-01：你在瀏覽器開 Pornhub 影片 →「🖧 交給節點」→ 節點下載成功、能播放
- U-02：Pornhub 網頁＋XVideos 的影片位址（不同網站）→ Master 建任務時就拒絕
- U-03：影片位址改成內網 IP 或清單外網域 → 拒絕
- U-04：電腦版沒開 Master →「交給節點」回清楚的錯誤
- U-05：舊版電腦版 → 腳本不顯示「交給節點」

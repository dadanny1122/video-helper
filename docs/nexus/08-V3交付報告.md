## 2. 驗證（都是實際跑過的）

- **單元＋整合測試**：Linux 約 290 個、Windows 約 300 個全過（nexus.yml 的 unit／windows job）
- **Windows 實測沙箱**：上限真的套用、子程序一開始就在 Job 裡、孫程序一起結束、關 handle 子程序跟著結束、600MB 配置被擋、程序數上限、檔案被開著時清理回報失敗、`C:`／`x:`／UNC 檔名跳不出資料夾
- **打包成 EXE 後**（nexus.yml `frozen` job，PyInstaller onefile）：isolation basic、寫檔搬運成功、取消後 EXE 程序數回到 2、0 殘留、環境變數白名單
- **真的 yt-dlp**：清單網域被解析到 127.0.0.1 → 被 socket 檢查擋下、分類成 NET_BLOCKED
- **ci_smoke 7b4**（build.yml，Windows，v1.31.0 發布前實跑）：用不存在的影片編號走完整條路 → `FAILED NOT_FOUND [XVideos] …: HTTP Error 404`、資料夾清乾淨。代表**沙箱裡的 yt-dlp 真的通過網路檢查連到了 xvideos.com**（網站回 404），不是被沙箱或網路檢查擋掉
- **發布**：v1.31.0 2026-11-23 發布；漏洞掃描無、網路流量測試全部在 SECURITY.md 清單內、EXE 自我測試 OK

## 3. 還沒驗證（照實說）

- **還沒從真網站實際下載過一部影片**：開發環境連不到成人網站；ci_smoke 7b4 確認了「沙箱裡連得到網站、會照實回報找不到」，但還沒走到「下載影片檔、合併、搬到下載資料夾」那段。要你實機驗收：
  - **T-06**：同一台電腦開 profile a／b，各派一部真的影片 → 各自下載到自己的資料夾、檔案能播放
  - **T-07**：下載到一半按取消 → 工作管理員裡沒有殘留的 VideoHelper／ffmpeg，節點的 `sandbox\work` 資料夾是空的
- **影片伺服器網域可能不全**：`sites.json` 的 media 清單沿用電腦版瀏覽器連動用的那份。某網站如果改用新的 CDN 網域，節點會回「NET_BLOCKED：xxx 不在支援下載的網站清單裡」→ 把網域加進 `sites.json` 就好
- 跨電腦（兩台不同電腦）一樣沒測（只有一台家用電腦）

## 3.5 實機驗收發現（2026-11-23）

- **Pornhub 節點下載做不到**：yt-dlp 開 Pornhub 網頁被回 **HTTP 410**（網站擋非瀏覽器程式；電腦版靠瀏覽器腳本送「影片真正的位址」繞過，節點只拿到網頁網址）。V3 規劃時漏想。v1.31.1：410／403 改成 `SITE_REFUSED`（不重試、附說明）。之後若要支援：Master 建任務時可以附「瀏覽器已經拿到的影片位址」（同電腦版 Bridge 的 media 欄位，網域照 `sites.json` media 檢查）→ 另開規格討論
- 錯誤分類漏掉 410 → 被當 ADAPTER_ERROR 重試了一次（已修）

## 4. 已知限制（規格裡就寫好、不是 bug）

- 檔案留在節點那台，不會傳回 Master（V4）
- 隔離等級是「基本」：不擋同一個 Windows 帳號下的惡意程式；資料夾權限用預設；網路限制在 Python 層
- 新版節點配舊版 Master（v1.30.x）派不到任務：兩邊一起更新
- 打包後每個下載任務的子程序會自己解壓一次（PyInstaller onefile），開始前多幾秒

## 5. 下一步建議

1. 你做 T-06、T-07 實機驗收（步驟在說明書「⬇ 下載影片（節點）」）
2. 驗收有問題就修 v1.31.x；沒問題再規劃 V4（檔案傳回 Master：大小、雜湊、續傳、Master 收檔的路徑檢查）

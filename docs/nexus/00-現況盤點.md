# Nexus Phase 0＋1：現況盤點（Repository Discovery／Current-State Audit）

依據《Video Helper Nexus 技術開發總規格書 v1.0》第 25.1 節的 Phase 0、Phase 1。
盤點日期：2026-11-15。所有結論都指向實際檔案（檔名:行號以當天 main 為準）。

## 0. 一句話

現在的 Video Helper 是「**一個 5,200 行的單檔 Tkinter 桌面程式 ＋ 一個 2,600 行的單檔瀏覽器腳本**」，
只在**自己這一台電腦**上跑，沒有任何跨機器的節點概念。規格書要的 Master／Worker 分散式平台，
現有程式裡**能直接沿用的大約兩成**（本機配對服務、錯誤分類與重試、狀態欄位、DPAPI 秘密保護、供應鏈流程），
其餘八成要新建。

## 2. 語言、框架、套件、打包

- Python 3.12（`build.yml:93`），GUI 是 **Tkinter＋ttk＋sv-ttk**（v1.25 起），單一主執行緒＋`queue.Queue` 把背景執行緒的結果丟回畫面（`App.poll`）。
- 直接依賴（`requirements.in`）：`yt-dlp`、`sv-ttk`、`pystray`、`pillow`、`truststore`、`pyinstaller`（＋Windows 專用 `pefile`、`pywin32-ctypes`）。
  **沒有** `cryptography`、`pydantic`、`fastapi`、`sqlalchemy`、`pytest`。
- 網路：全部用標準庫 `urllib`／`http.server`／`socket`；TLS 用 `truststore.inject_into_ssl()`（:44）走 Windows 憑證庫。
- 打包：`pyinstaller --onefile --windowed`（`build.yml:165`），產物 `VideoHelper.exe`；`requirements.txt` 鎖版＋sha256（`--require-hashes`）→ pip-audit → CycloneDX SBOM → `actions/attest-build-provenance`＋`attest-sbom` → Release。
- 迷你 ffmpeg 自己編（`.github/ffmpeg/build.sh`，LGPL）。
- `build.yml` 只在 `video_helper_app.py`、`ci_smoke.py`、`ffmpeg/**` 改動時觸發（`build.yml:7-11`）→ **新增 `nexus/` 套件後必須加進 paths，否則不會重新打包**。

## 3. 現有資料流

```
瀏覽器腳本 ──(127.0.0.1:47321～47325, Bearer token)──▶ Bridge(:913) ──▶ TaskQueue(:619) ──▶ pump() 一次一個
                                                                        │                      │
                                                                        ▼                      ▼
                                                       settings.json / history.json      run_download()（yt-dlp 或自寫分段下載）
                                                       stats.json / decisions.jsonl             │
                                                                                                ▼

```

- 所有狀態檔在 `%APPDATA%\VideoHelper\`（`data_dir()` :132）：`settings.json`、`history.json`、`stats.json`、`decisions.jsonl`、`video_helper.log`（依 `log_keep_days` 輪替，:693）。
- **下載佇列只在記憶體**（`TaskQueue` :619 沒有持久化）；程式關掉未完成的任務就消失，只有半成品檔案靠 `dest.parts.json` 續傳。

## 5. 主要耦合與技術債（會影響 Nexus 的）

1. **單檔 5,200 行、GUI 與邏輯混在一起**：`App` 類別（:3086 起，約 2,100 行）同時管畫面、佇列、下載執行緒、Bridge 回呼。Nexus 若也塞進去會失控 → 必須新開 `nexus/` 套件，`App` 只負責「顯示＋呼叫」。
2. **狀態不是單一入口**：`t["status"] = …`／`t.update(status=…)` 散在 15 處（grep 結果）。規格 11.2 要求單一入口＋樂觀鎖＋同交易寫 audit → Nexus 的任務狀態機要**重新設計**，不能直接改現有 `TaskQueue`（會破壞既有下載）。
3. **沒有資料庫**：全部 JSON 整檔覆寫（`Settings.save`、`History.save`）。多個 Worker 的任務、事件、稽核需要交易與唯一約束 → 新增 SQLite（標準庫，不加依賴）。
4. **Bridge 只綁 127.0.0.1、純 HTTP**（:938）：對瀏覽器夠用；對跨機器完全不夠（沒有 TLS、沒有對端身分）。**不能把 Bridge 直接改成綁 0.0.0.0**，那會把現在靠「只有本機能連」撐起的安全假設整個打掉。
5. **沒有測試框架、沒有 lint**：規格 23 要 Lint／Type Check／Unit／Integration。要先補 pytest＋ruff，否則「先測試後實作」做不到。
6. **UI 文字與功能綁死**：說明書、Discord 公告都用 ①②③④ 分頁名；Nexus 的 GUI 放在「⚙ 進階設定」新分頁最不侵入。
7. **執行緒模型**：Bridge 的 `ThreadingHTTPServer` 每個請求一個執行緒，直接讀寫 `settings`（有 `self.lock` 但只保護配對）。Master API 若沿用，SQLite 要每執行緒一個連線或用佇列序列化。
8. **更新機制只是通知**：`check_update` 只查 GitHub Releases 最新版號、開網頁（:1246）；沒有自動下載，所以「更新檔驗簽章」目前不適用，但也代表 Worker 版本不一致會很常見 → 版本相容檢查（規格 20）一定要做。

## 6. 安全現況（與規格第 4、16 節對照）

- ✅ 已有：本機服務需配對、token 雜湊儲存、一次性配對碼、Origin／自訂標頭檢查（v1.18.2）、DPAPI、第三方元件雜湊、連線白名單測試、SBOM／attestation、腳本隱私測試。
- ⚠️ 部分：日誌遮罩（只有網址）、速率限制（只有配對）、稽核（一般日誌，非結構化、可被覆寫）。
- ❌ 沒有：TLS 服務端、對端身分、RBAC、路徑穿越防護（目前輸出檔名由 yt-dlp 清理，沒有自己的 artifact root 檢查）、程序沙箱（yt-dlp 在同一個 Python 程序裡跑，ffmpeg 是子程序但沒有 Job Object）、網路隔離、程式碼簽章。
- 威脅模型文件：`SECURITY.md` 有「資料外傳清單」與「本機服務防護」，但**沒有**跨機器的威脅模型。

# 一鍵檢查 EXE、whisper.cpp 寫死指紋 — 規格草稿

> 2026-11-24｜來源：使用者轉來的供應鏈安全評論（建議「把 attestation 驗證做成電腦版內建的一鍵檢查」）。
> 狀態：**草稿，等使用者確認 S1～S5**。程式碼簽章（不開放台灣個人）、可重現建置（效益低）先不做。

## 1. 決策（請確認）

| # | 問題 | 建議 |
|---|---|---|
| S1 | 一鍵檢查放哪 | 「🔒 安全與統計」頁的「元件和指紋」卡片，按鈕「🔍 檢查這個 EXE 是不是官方打包的」 |
| S2 | 怎麼檢查 | ① 算自己這個 EXE 的 SHA-256 → ② 問 GitHub `api.github.com/repos/dadanny1122/video-helper/attestations/sha256:<指紋>` 有沒有本專案的簽章紀錄 → ③ 再比對這一版發布頁上 VideoHelper.exe 的指紋（GitHub 幫每個發布檔算的 digest）。兩個都對得上＝✅ |
| S3 | 誠實標示 | 結果寫清楚：「這是去 GitHub 查紀錄，不是在你電腦上做完整的密碼學驗證；要完整驗證請用 `gh attestation verify`」。不裝 sigstore 這類大套件 |
| S4 | 什麼時候檢查 | 只有按按鈕才連網（不自動、不在背景偷偷查）；結果記在 🔒 頁，不存檔 |
| S5 | whisper.cpp | 改成固定一個版本（目前最新版），下載網址和 SHA-256 寫死在程式裡（跟 AI 模型一樣）；GitHub 上的 digest 也要對得上（兩道）。whisper 出新版時要作者手動更新指紋 |

## 2. 會連到哪裡

- 只有 `api.github.com`（已經在 SECURITY.md 第 1 節和 `net_test.py` 的允許清單裡，檢查更新本來就會連）
- 送出去的只有：EXE 的 SHA-256 指紋（公開資訊）、版本號；不送任何個人資料

## 3. 結果的幾種情況

| 情況 | 顯示 |
|---|---|
| 有簽章紀錄＋發布頁指紋一樣 | ✅ 這個 EXE 是 GitHub Actions 從本專案原始碼打包的（第 N 次打包、時間） |
| 沒有簽章紀錄 | ❌ GitHub 查不到這個 EXE 的打包紀錄：可能被改過或不是從官方下載的，建議重新從發布頁下載 |
| 有紀錄但發布頁指紋不同 | ⚠ 跟發布頁的不一樣（可能是舊版或發布頁被動過），附兩個指紋 |
| 不是 EXE（直接跑 .py） | 這個功能只檢查打包好的 VideoHelper.exe |
| 連不到 GitHub／太多次 | 說明原因，請稍後再試 |

## 4. 測試

- 單元：假的 GitHub 回應（有紀錄／沒紀錄／指紋不同／404／限流）→ 顯示對的結果
- Windows CI：打包完用真的 EXE 跑一次 `--verify-self`（新增的命令列參數，不開視窗），要得到 ✅（剛打包、attestation 剛簽好；放在簽章步驟之後）
- whisper：build.yml 現有的「AI 字幕實測」會真的下載寫死的版本，指紋不對就不發布

# S3 相容性矩陣 — 規格（2026-11-25 使用者確認，已完成）

目的：新版發布前，自動確認「一邊更新、另一邊還沒更新」時不會壞。
（朋友的腳本會自動更新，但電腦版要手動下載 → 新舊混用一定會發生）

## 要測的組合

| # | 組合 | 怎麼拿到舊版 | 要通過 |
|---|---|---|---|
| C1 | 新電腦版 × 上一版腳本 | 腳本：上一個 `userscript-v*` tag | `/ping` 能讀、配對、送到電腦版（enqueue）、查狀態 |
| C2 | 上一版電腦版 × 新腳本 | 電腦版：上一個 `v*` Release tag 的原始碼（用 `git worktree`，不下載 EXE） | 同上；新腳本若要用舊電腦版沒有的功能 → 顯示「請更新電腦版」，不能當掉或亂送 |
| C3 | 新 Master × 上一版 Worker | 同 C2 的舊原始碼跑 `--worker` | 配對 → 核准 → 心跳 → 派 `test.echo` 成功 → 撤銷斷線 |
| C4 | `LEGACY_FEATURES`／`LEGACY_SITES` 表 | 假的 `/ping` 回應（沒有 features 的舊版、1.12／1.15／1.16 等） | 每個功能、每個網站判斷「有／沒有」都對 |

「上一版」＝比這次要發布的版本小的最近一個 tag；第一次跑時若某一版的測試程式本身跑不起來，標「跳過＋原因」，不算失敗。

## 放在哪裡

- 新檔 `.github/compat_test.py`（C1～C3 的總指揮）＋ `.github/compat_test.js`（Playwright 載入指定版本的腳本、跑 C1／C2／C4）
- 沿用 `attack_bridge.py` 的「只啟動 Bridge」方式，加參數指定用哪份原始碼
- 接到 `build.yml`（電腦版要發布前）和 `userscript.yml`（腳本升版前）：**失敗就不發布**
- C3 也加進 `nexus.yml`

## 不做（照 S2 的限制延續）
- 不改 Bridge API、不改 Nexus 協定、不改安裝／更新方式
- 只測「上一版」，不測所有歷史版本（太慢；需要時可手動指定版本跑）
- 不測 EXE 本身（Linux 上跑原始碼；EXE 已有 ci_smoke／net_test）

## 完成條件
- C1～C4 在 CI 綠燈，失敗會擋發布
- 規劃文件 S3 標 ✅，回報每個組合實際測到的版本號
